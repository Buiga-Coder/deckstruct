# Интеграция команды

## Что есть и что нужно согласовать

P5.html содержит `MockBackend`, `HttpBackend` с `/api` и отдельный `DesignSystemAPI`. Оба пока используют mock. Переключать оба адаптера на HTTP только после реализации соответствующих маршрутов. Форма загрузки шаблона уже использует multipart поле `file`.

| Область | Маршруты, ожидаемые текущим фронтом |
| --- | --- |
| Авторизация | POST `/api/auth/register`, `/api/auth/login`, `/api/auth/reset`; GET `/api/auth/me` |
| Профиль | PATCH `/api/profile` |
| Шаблоны | GET/POST `/api/templates`; DELETE `/api/templates/{id}` |
| Презентации | GET/POST `/api/decks`; DELETE `/api/decks/{id}`; GET `/api/decks/{id}/download` |
| Дизайн-системы | отдельный адаптер `DesignSystemAPI.http` в HTML; согласовать с автором парсера |

Это описание существующего интерфейса, не готовый контракт backend. JSON ошибок должен содержать `message`. Точные схемы запросов и ответов зафиксировать в OpenAPI вместе с разработчиками.

## Предлагаемый сквозной процесс

1. Загрузка PPTX → валидация размера/архива → парсер → JSON со структурой и стилем.
2. Загрузка материалов → извлечение текста → план слайдов через LLM.
3. Сборка настоящего PPTX по результату парсера → проверка файла → скачивание.

Генерацию выполнять в фоновой задаче: POST возвращает `job_id`, фронт опрашивает статус. Это потребует изменения текущего синхронного `createDeck` и индикатора прогресса. Ограничить очередь и число одновременных генераций. Добавить таймауты, понятные ошибки, повтор только временных сбоев и кэширование результатов парсинга по хэшу шаблона.

## Парсер

Источник разработчика: https://github.com/daniilboriskin21-eng/pptx-template-parser.git

Проверен авторизованным Git 27.09.2026, commit `7480f452373cf6f38018becf35823847559b08c8`, пакет Python `pptx-template-decomposer` версии 0.3.0. Код скачан для анализа отдельно; в общий проект пока не импортирован. Вместе с автором выбрать версионированную зависимость или подключение отдельного сервиса.

**Критическое ограничение:** полный цикл рендера требует Windows и установленного настольного Microsoft PowerPoint. `template_parser/render.py` явно отклоняет другую ОС; Linux-рендер не реализован. На текущем Ubuntu VPS модуль целиком не заработает без доработки. Для хакатона можно оставить worker на Windows-машине разработчика и подключить к backend защищённым каналом; альтернатива — разработать и проверить рендер через LibreOffice.

Парсер уже имеет фоновое HTTP API на `127.0.0.1:8765` с токеном `PARSER_API_TOKEN`: POST `/jobs` принимает **сырой PPTX**, GET `/jobs/{id}` возвращает состояние, POST `/jobs/{id}/resume` продолжает работу, маршруты `/jobs/{id}/versions/{version}/result` и `/package` отдают JSON и ZIP. Локальное API нельзя просто открыть в интернет: в нём нет пользовательской изоляции.

Нужен серверный адаптер между multipart `/api/templates` фронта и raw body `/jobs` парсера, отображение статусов и передача `job_id + version` генератору. Сам парсер новую презентацию не создаёт. Для семантического анализа требуется **VLM с поддержкой изображений**, обычной текстовой LLM недостаточно.

В CLI между слайдами по умолчанию есть пауза 10 секунд (`--delay`), а обработка 429 дополнительно ждёт и повторяет запросы. Сначала измерить вклад этих задержек, рендера и самого VLM. Уменьшать паузу только с учётом лимитов провайдера; это не исправит перегруженный API.

## LLM

Сервер 94.228.166.245: 1 vCPU, 1968 МБ RAM, около 1,1 ГБ доступно на момент проверки; вычислительного GPU нет. На нём уже работают шесть контейнеров ВК-проекта. Инференс на этом сервере не развёрнут: качество и задержка подходящей для презентаций модели здесь не подтверждены, запас ресурсов слишком мал.

Предлагается отдельный компьютер/GPU-сервер с Ollama или другой совместимый API. Переменные будущего backend: `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`. Ключ хранить только в окружении backend; браузер обращается к вашему `/api`, не к модели напрямую. Значения `.env.example` — заготовка, контейнер фронта их не использует.

Ollama предоставляет совместимый маршрут `/v1/chat/completions`: https://docs.ollama.com/api/openai-compatibility . У локального Ollama API-ключ не обеспечивает авторизацию: доступ давать через закрытую сеть/SSH-туннель или защищённый шлюз. Из контейнера `127.0.0.1` указывает на сам контейнер, поэтому backend должен получить доступный ему адрес LLM.

До выбора модели измерить задержку на реальном русском тексте и шаблоне: время первого токена, полное время генерации, корректность JSON и результат сборки PPTX. Локальная модель сама по себе не гарантирует ускорения.

## Что нужно от команды

- Пример PPTX + ожидаемый JSON парсера и доступ остальных участников к его репозиторию.
- Стек и текущий код второго разработчика; кто собирает PPTX.
- Один общий образец материалов и эталон результата для сквозной проверки.
- GitHub-имена участников для выдачи доступа; домен для HTTPS.

До перехода к реальным аккаунтам: HTTPS, серверное хранение хэшей паролей, ограничения файлов и авторизация скачивания. MockBackend хранит введённые тестовые пароли в localStorage и не является системой авторизации.
